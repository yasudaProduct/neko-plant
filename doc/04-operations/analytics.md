# 計測と改善プロセス

本番運用でユーザーを増やし、改善を回すための**指標の定義**と**振り返りの手順**をまとめます。
監視・バックアップなど「落ちていないか」を見る話は [monitoring.md](./monitoring.md) にあります。

## 基本方針

**指標は2層に分けて持ちます。**

| 層 | 何を測るか | 置き場 | 理由 |
| --- | --- | --- | --- |
| **DB由来** | 結果として起きたこと（投稿・登録・いいね） | `/admin` の集計 | ベンダーに依存せず、後からいつでも遡って再集計できる |
| **行動イベント** | DBに残らない途中の行動（離脱・検索語・押下） | GA4 | 「起きなかったこと」はDBに記録されない |

DB由来を**正**とします。GA4 は広告ブロッカーで欠測するため、
投稿数のような重要指標を GA4 の数字で語らないでください。

## North Star

**週次の「猫と植物の両方がタグ付けされた投稿」数。**

このサービスの価値は共存実績の蓄積であり、実績は投稿からしか増えません。
閲覧数やユーザー数はその結果か、前段の指標です。
`posts` は投稿時に植物1つ以上・猫1匹以上を必須にしているため、実質的には週次投稿数と一致します。

## 指標の一覧

| 段階 | 指標 | 取得元 | 状態 |
| --- | --- | --- | --- |
| 集客 | 植物ページへの検索流入、検索クエリ | Search Console | 要登録 |
| 集客 | 参照元別のセッション | GA4 | 取得済み |
| 登録 | 週次の新規ユーザー数 | `users.created_at` | 集計を書けば取れる |
| 活性化 | 登録 → 猫登録 → 初投稿 の転換率 | `users` / `pets` / `posts` | 同上 |
| 活性化 | 投稿フローの離脱段階 | GA4 イベント | **未実装** |
| 継続 | 投稿者の翌週再投稿率 | `posts` | 集計を書けば取れる |
| 継続 | 週次のいいね数、いいねした人数 | `post_likes` | 同上 |
| データ価値 | 共存実績のある植物数、ユニーク猫数 | 既存の集計クエリ | `getSiteStats()` が近い |
| AI | 判定の実行回数 | `plant_identification_logs` | 取得済み |
| AI | 候補の採用率（提示した候補が選ばれた割合） | — | **未実装。スキーマ変更が必要** |

### 転換率の定義

分母を「その週に登録したユーザー」に固定したコホートで見ます。
「全ユーザーのうち投稿した人の割合」は、新規が増えるほど下がるので改善の判断に使えません。

| 転換 | 定義 |
| --- | --- |
| 猫登録率 | 登録から7日以内に `pets` を1件以上作った割合 |
| 初投稿率 | 登録から7日以内に `posts` を1件以上作った割合 |
| 再投稿率 | 初投稿した週の翌週にも投稿した割合 |

## 実装の指針

### DB由来の集計

`/admin` に週次の推移とコホート転換率を出します。Prisma 経由なので RLS は関係ありませんが、
**管理者判定は `/admin` の他ページと同様にサーバー側で行ってください**
（[admin.md](./admin.md) 参照）。

集計クエリは重くなりがちです。`posts.created_at` には既に降順インデックスがあります。
ユーザー数が数千を超えたら、日次のスナップショットテーブルを作ることを検討します。

### GA4 イベント

`@next/third-parties` の `sendGAEvent` を使います。GA4 は `NEXT_PUBLIC_GOOGLE_ANALYTICS_ID`
が設定されているときだけ読み込まれるため、未設定の環境ではイベントも飛びません。

**イベントは「DBに残らない行動」だけに絞ります。** 投稿完了のようなDBに残る事実を
GA4 でも数えると、二重管理になったうえ数字がずれて混乱のもとになります。

| イベント名 | 送る場所 | 何がわかるか |
| --- | --- | --- |
| `post_flow_step` | 投稿フローの各ステップ到達 | どこで離脱しているか |
| `post_flow_abandon` | 投稿フローの離脱 | 同上 |
| `plant_search` | 植物検索の実行（検索語つき） | 何を探しに来ているか |
| `plant_search_zero` | 検索0件 | 足りていない植物 |
| `ai_identify_used` | AI判定の実行と結果採用 | AIが役に立っているか |
| `share_click` | シェアボタン押下 | 拡散の起点 |

**個人を特定できる値をイベントに載せないでください。** 検索語はユーザーの入力なので、
自由記述のコメント本文などは絶対に送らないこと。プライバシーポリシーの記載範囲を超えます。

### 計測を足すときのルール

外部の計測サービスを追加する場合、**2箇所の更新が必須**です。

1. **CSP** — `src/lib/supabase/middleware.ts`。本番は nonce ベースで `script-src 'self'` のみです。
   外部スクリプトを読む計測ツールはそのままでは動きません。
2. **プライバシーポリシー** — `src/app/privacy/page.tsx` の第三者提供の記載。

## 改善ループ（週次・30分）

1. **数字を見る** — `/admin` の週次、GA4 の参照元、Search Console のクエリ。
2. **定性を見る** — Notion のお問い合わせ、SNSのメンション、自分で投稿したときの引っかかり。
3. **仮説を1〜2個に絞る** — [../05-backlog/growth-backlog.md](../05-backlog/growth-backlog.md) に追記する。
4. **作って出す** — PRに「どの指標を動かす想定か」を1行書く。
5. **翌週に前後を見る** — 判断は「明らかに動いたか」だけ。母数が小さいうちは有意差を語らない。

**A/Bテストは当面やりません。** 週の投稿数が2桁のうちは、群を分けても差が検出できません。
その規模では、5人にインタビューするほうが速く確実です。

### ユーザーインタビュー

投稿してくれた人に15分。最初の2か月で5人を目標にします。聞くのは事実だけです。

- 何をしようとしてこのサイトに来たか
- 実際にやったこと、詰まったところ
- 今使っている代替手段（Instagram、検索、書籍）

「どう思いますか」「この機能欲しいですか」は聞きません。答えが当てになりません。
